MtG Goldfish Simulator

A solitaire (“goldfish”) Magic: the Gathering simulator with a web interface. Give it a deck and a set of properties written in plain English — it exhaustively explores every line of play and measures how often those properties can be satisfied.

Get the code Write your first property

Not a “good pilot”

The simulator does not try to play well. It is a search engine over the decision tree of a solo game: it tries every legal sequence of decisions and counts the ones that reach your target state.

Real rules engine

Turn structure, the stack, mana payment, commander tax, fetchlands, activated and triggered abilities, tokens, combat against a phantom opponent — with per-card behaviour implemented one file per card.

English → code

Properties are written in plain English (“the commander is in play and 4 non-creature spells were cast this turn”) and compiled to Python by an LLM — reviewable before running.

From deck URL to statistics

The data flows in one direction. You import a deck, describe what you want to observe, and the engine answers with a success rate and replayable winning lines.

How a simulation runs

A run plays N independent games. Each game is one random shuffle of the deck (seeded, so runs are reproducible). For each game the engine then searches the whole decision tree:

  1. Mulligans. If you allow Y mulligans, every way of bottoming Y cards of the opening 7 becomes a separate root of the search.
  2. Lines of play. At every point the player has priority, every legal action is a branch: in a main phase, playing a distinct land (with its enter modes — a shockland can enter tapped or cost 2 life), casting a distinct affordable spell, activating an ability, or passing. In the other steps (upkeep, combat sub-steps, end step) an instant-speed window opens whenever an instant, a flash spell, or an instant-speed ability is actually available — so lines like cracking a fetchland on the end step, or holding up a counterspell, are explored too. Fetch targets, tutor targets, discards, X values, modal choices and attack declarations branch as well.
  3. Mana is not a branch point. Tapping sources to pay a cost is solved deterministically by a payment planner, keeping the tree focused on genuinely meaningful decisions.
  4. Checkpoints. The game state is checked against your properties at every phase entry and after every action at a priority window.

A game is a success if some single line satisfies all properties at their respective trigger moments. Independently, per-property statistics count the games where each property was satisfiable in any line.

Pruning & bounds

  • Viability pruning: a branch is dropped the moment any unsatisfied property can no longer be verified on it (its “at” moment is past, or its “before” deadline reached) — no descendant could make the game a success.
  • Sticky satisfaction: once a property holds at one of its checkpoints on a line, it stays satisfied on that line; the search stops as soon as every property is verified.
  • Budget: each game runs until every property is satisfied, no branch can satisfy them anymore (the frontier drains), or a wall-clock timeout — there is no node cap. Timed-out games are reported as such (⏱ in the runs table).
  • Bugs are logged, never hidden. If a card's behaviour raises mid-action the branch is recorded as an error (⚠ in that game's tree) and the game keeps searching other lines; the number of bugs hit is surfaced per game in the runs table (🐛), with the full traceback one click away — so a buggy card can't silently swallow otherwise-viable lines.

Search strategies

All strategies are exhaustive — they visit the same states, only the order differs, so winning lines are found sooner and timeouts bite later:

ModeOrder
best_first default Greedy best-first on a board-progress score (satisfied properties, then permanents in play, cards seen, turn) — heads for the most developed states first.
dfs_heuristic DFS with move ordering: lands → commander → tutors/fetches → other spells → abilities → pass; mulligan keeps closest to 3 lands first.
dfsDFS in natural action order.
bfsBreadth-first — shallowest lines first.

Spells, abilities and the stack

The engine models the stack the way the game does:

  • Casting a spell pays its full cost first, then puts the card on the stack (cast triggers fire), then it resolves — permanents enter the battlefield, other spells go to the graveyard as their effect applies.
  • Activated abilities pay their costs (tapping, sacrificing, mana, life) at activation time, before the ability goes on the stack. The effect applies at the moment the ability resolves — in a single step.
  • Triggered abilities (ETB, landfall, upkeep, attack triggers…) are put on the stack when their event happens and apply their effect when they resolve.
  • Replacement effects never use the stack: a land that “enters with two depletion counters” has them from the moment it enters.
  • Mana abilities don’t use the stack either — they are solved inside the payment planner.

The board viewer shows the stack zone live during replays, so you can watch spells and abilities go on and come off it, step by step.

Installing & running it

No programming experience needed — install one small free tool (uv, which brings its own Python), download the project, and run a single command:

uv run mtg-goldfish        # then open http://127.0.0.1:8000 in your browser

The full step-by-step guide — installing uv on macOS / Windows / Linux, downloading the project (no Git required), running it, updating, and troubleshooting — is on the Install page.
